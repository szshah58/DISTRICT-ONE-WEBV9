3. AUTHORIZATION ARCHITECTURE VERIFIED IN SOURCE

- UserPermissionService checks active account, access start/end timestamps,
  active designation, and department compatibility. Designation permissions
  come from webv9_position_permissions; individual user overrides take
  precedence, including an explicit deny. Role permissions are not inherited
  by the effective permission resolver. A granted Reports/VIEW action is
  included in the effective module list for scoped users.
- Super Admin is determined from the active user super-admin flag or
  SUPER_ADMIN role and receives the existing system-wide permission bypass.
- ProjectAccessService checks active project/location/city assignment,
  account dates/status, designation activity, and department compatibility.
  accessibleProjectIds supplies the active project set used by the new
  reports.
- PermissionAuthorizationFilter checks the required module/action before
  controller execution. New reports require Reports/VIEW and, for the
  underlying data, Finance/VIEW or Plots & Sales/VIEW. Report queries separately
  restrict the records to permitted project scope.
- Auth/current-user data exposes effective modules and permission actions to
  the frontend. The frontend hides unauthorized navigation and report choices;
  backend checks remain authoritative.
- Finance receipt actions are distinct: RECEIPT_CREATE, RECEIPT_VERIFY,
  RECEIPT_POST, and RECEIPT_REVERSE. Verification, posting, and reversal are
  not inferred from a Finance role name.

5. PERMISSION / ROLE / DESIGNATION DISCREPANCIES

VERIFIED IN SOURCE CODE

1. Role permissions and effective authorization can disagree. The
   administration options API exposes role_permissions for display, while
   UserPermissionService resolves effective access from designation grants
   and user overrides. A displayed role permission is not by itself an
   effective grant.
2. The generic Admin function is narrower than the requested scoped Admin
   model: system-wide Admin & Settings endpoints remain Super-Admin-only.
   The scoped user-management helpers do not make all administration
   endpoints scoped.
3. The frontend is a usability layer. Not every legacy action/control has
   been audited for visibility against the full action matrix. Backend
   authorization prevents unauthorized API execution, but a user may still
   see an unusable legacy control.
4. The Reports UI displays only report types for which the current session
   has the source module in addition to Reports. Backend separately checks
   Reports/VIEW and the source module's VIEW right.
5. Reports exceeding 1,000 results are truncated. Summary values are from
   returned rows and explicitly identified as partial. No server-side
   pagination or full-result export is implemented.
6. Spreadsheet output is Excel-compatible HTML (.xls), not XLSX. PDF is
   browser Print / Save as PDF. Neither is a server-side export pipeline.
7. The legacy /api/v1/reports/summary and Dashboard are system-wide,
   Super-Admin-only surfaces, not scoped reports.

NOT VERIFIED

- Any actual username, account status, job designation, department, role,
  user-level override, project/location scope, access start/end date, or
  effective permission.
- Whether deployed tables/columns and workflow statuses match the source SQL.
- Whether Admin or other existing assignments depend on legacy role grants.
- Whether every legacy customer-care, ledger, sales, and finance query enforces
  exactly the desired per-record location scope.
- Whether the business intends distinct permissions for approve, cancel, and
  reverse across modules beyond the existing generic action mapping.
- Whether current user/designation assignments should be migrated or corrected.
