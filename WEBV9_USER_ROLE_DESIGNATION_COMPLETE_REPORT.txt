4. VERIFIED IN SOURCE CODE: EFFECTIVE VS ADMIN-UI PERMISSIONS

4.1 Permissions displayed by the admin detail view

OperationsController user detail includes a permission if there is a positive per-user
override, or (when the user has a position) a designation permission, or (only when no
position is set) a role permission. An explicit false override is omitted from the display.
The same response returns role, department, dates, designation and project scopes.
[backend\src\main\java\com\districtone\webv9\controller\OperationsController.java:160-193]

4.2 Permissions used by the API permission filter

UserPermissionService gives SUPER_ADMIN/is_super_admin a complete grant. Otherwise it uses
an explicit override when present, then falls back to role_permissions. It does not consult
webv9_position_permissions. [backend\src\main\java\com\districtone\webv9\security\UserPermissionService.java:16-38]

Confirmed consequences:
- A designation-only permission can be displayed but is not by itself granted by
  UserPermissionService.
- With a designation assigned, the UI display calculation excludes a role permission
  unless a positive user override exists; API permission resolution may still grant that
  same role permission if there is no override. The UI can therefore hide an effective grant.
- A false override is honored by UserPermissionService but omitted from the detail response's
  displayed permission list.
- The access-assignment path only inserts positive overrides after deleting old ones. An
  omitted role permission has no explicit false override and falls through to role grant.
- The special SUPER_ADMIN/is_super_admin bypass is broad. Whether this privilege is
  appropriately assigned is not verified without live records.

4.3 Role and designation reload behavior

- Staff JWT requests reload users.role from the database, so role changes can affect the
  next request. Position data is not reloaded because the query projects NULL as
  position_code. Department-derived ROLE_FINANCE/RECOVERY/STAFF/CUSTOMER_CARE code is
  therefore unreachable for staff in the current query path.
  [JwtAuthenticationFilter.java:55-78]
- The database role is not taken from the JWT for staff requests after token parsing; the
  current account role is used. Whether all endpoints consistently use this identity is a
  separate source audit question.

5. AUTHORIZATION AND BUSINESS FUNCTION FINDINGS

Finding A - Designation grants are not effective API grants.
Classification: VERIFIED IN SOURCE CODE. Actual affected users: NOT VERIFIED.
UserPermissionService omits the designation permission table while the admin UI reads it.
References: OperationsController.java:179-188; UserPermissionService.java:16-38;
JwtAuthenticationFilter.java:55-64.

Finding B - Scope rows do not authorize non-Super-Admin accounts.
Classification: VERIFIED IN SOURCE CODE. Actual affected users: NOT VERIFIED.
canAccessProject, canManageScope, and canManageUser return only a Super Admin check; they do
not query webv9_user_project_scopes. Stored scope rows therefore cannot make a non-Super-Admin
pass those checks. References: backend\src\main\java\com\districtone\webv9\security\ProjectAccessService.java:31-51;
OperationsController.java:190-193, 358-365.

Finding C - Start/end dates and later designation deactivation are not enforced at login/API
authentication.
Classification: VERIFIED IN SOURCE CODE. Actual assignments: NOT VERIFIED.
The code persists dates and validates only their ordering in assignment/create code.
AuthController and JwtAuthenticationFilter check active account/password or is_active only.
References: OperationsController.java:328, 356, 431, 453;
AuthController.java:46-66; JwtAuthenticationFilter.java:55-58.

Finding D - Role grants can remain despite exclusion from the access assignment selection.
Classification: VERIFIED IN SOURCE CODE. Actual users: NOT VERIFIED.
The assignment endpoint clears overrides and writes positive selected grants; UserPermissionService
then falls back to role_permissions for permissions with no override.
References: OperationsController.java:367-372; UserPermissionService.java:21-24, 33-36.

Finding E - UI admin permissions and API authorization differ.
Classification: VERIFIED IN SOURCE CODE. Actual affected users: NOT VERIFIED.
The admin detail view's permission list differs from UserPermissionService as described in
section 4. References: OperationsController.java:179-188; UserPermissionService.java:16-38.

Finding F - Super Admin/ADMIN user-management role annotations conflict with scope helpers.
Classification: VERIFIED IN SOURCE CODE. Runtime results for accounts: NOT VERIFIED.
`/admin/users` allows SUPER_ADMIN, ADMIN and DEPARTMENT_MANAGER at the method annotation,
but filters through canManageUser, which returns true only for Super Admin. Other detail/
assignment paths also use this helper.
References: OperationsController.java:148-158, 160-177, 288-313;
ProjectAccessService.java:50-51.

Finding G - Frontend account form does not maintain designation/scope/access dates.
Classification: VERIFIED IN SOURCE CODE.
The standard admin form exposes department, role, permission checkboxes and active status;
it submits create/update payloads without positionId, access dates or projectScopes. Backend
non-Super-Admin create requires position and at least one scope. The dedicated access
assignment API has no frontend call found in main.tsx.
References: frontend\src\main.tsx:3976-4005;
OperationsController.java:254-288, 408-410.

Finding H - DATA_ENTRY form default conflicts with finance receipt-entry API role gate.
Classification: VERIFIED IN SOURCE CODE; actual role catalog/user assignment: NOT VERIFIED.
The form selects DATA_ENTRY when that role exists; FinancePaymentController's class-level
PreAuthorize excludes DATA_ENTRY, while the UI receipt entry calls `/finance/recovery`.
References: frontend\src\main.tsx:3980-3987, 2251;
backend\src\main\java\com\districtone\webv9\controller\FinancePaymentController.java:33-35, 335.

Finding I - Customer Care role behavior is not consistently designation-based.
Classification: VERIFIED IN SOURCE CODE; role/department mapping records: NOT VERIFIED.
CustomerCareController accepts CUSTOMER_CARE as a role. JwtAuthenticationFilter contains a
department-to-role mapping after reading position_code, but that projection is NULL. A user
may still receive the authority from users.role. References: CustomerCareController.java:25-27;
JwtAuthenticationFilter.java:55-78.

5.2 Finance separation of duties

Source code confirms separation checks for the receipt lifecycle:
- Verify/reject requires an active users.role in SUPER_ADMIN, ADMIN, FINANCE and refuses the
  entry creator. [backend\src\main\java\com\districtone\webv9\service\FinanceVerificationService.java:40-42, 72-76, 136-140]
- Post requires an active Finance-authorized role and refuses both entry creator and verifier.
  [backend\src\main\java\com\districtone\webv9\service\AllocationBasedPaymentPostingService.java:24-45]
- Reverse requires an active Finance-authorized role and refuses the entry creator or verifier.
  [backend\src\main\java\com\districtone\webv9\service\PaymentReversalService.java:30-47, 110-116]
- These checks use users.role, not designation-derived effective permissions.

Whether all payments and current accounts satisfy these policies is NOT VERIFIED. The source
paths examined enforce a different actor for entry vs verify, and entry/verifier vs post/reverse.
