SCOPE AND LIMITATIONS

This is a source-code review of the frontend, controllers, authorization
services, workflow repository, and checked-in SQL files. No live database
connection was available; actual schema version, user assignments, rows,
transaction statuses, and runtime SQL compatibility are NOT VERIFIED. No
customer/financial records or database objects were changed.

The report catalogue distinguishes:
- IMPLEMENTED: a report or report-like query exists and can return real source
  data.
- PARTIALLY IMPLEMENTED: an operational list or summary exists, but requested
  filters, totals, reconciliation, export, scoping, or business status detail
  are incomplete.
- MISSING: no safe source implementation or supported data model was found.

New Reports workspace export controls operate only on rows returned by the
authorized API (maximum 1,000 per request): CSV, Excel-compatible HTML with an
.xls extension, and browser Print / Save as PDF. This is not a native XLSX or
server-generated PDF service. When a result is truncated, the screen warns
that displayed summary totals cover only the returned rows. The new controller
SQL was tested with mocked JDBC, not executed against a live database.

EXECUTIVE SUMMARY

The Reports navigation and filterable workspace now provide:
1. Plot inventory.
2. Plot merging register/history.
3. Plot cancellation/refund register.
4. Overdue receivables aging.
5. Finance receipt register.

These are real-source reports, not demo or placeholder rows. The new endpoints
require Reports/VIEW and the relevant source-module VIEW right; report SQL
limits rows to active project/location scopes. CSV, Excel-compatible .xls,
and print/PDF are browser-side actions over the returned data.

The existing application also has operational screens and APIs for bookings,
transfers, payment verification/posting, customer statements, customer-care
cases, audit logs, and configuration. Most are not formal reports and do not
have the new export/summary behavior.

Required surcharge-waiver, project/location summary, cashbook, advances,
plot/possession aging, and cancellation-trend reports are NOT IMPLEMENTED
because a suitable authoritative source/report model was not identified.
In particular no surcharge-waiver request/approval/posting entity or checked-in
SQL schema was found. Requested/approved adjustments must not be re-labelled
as posted waivers.

B. NEW REPORT DETAIL AND RULES

1. Plot Inventory

GET /api/v1/reports/plots/inventory calls the existing PlotInventoryService
once per active project returned by ProjectAccessService.accessibleProjectIds.
An explicit project ID outside that list returns no data and does not query the
inventory service. Search/status/availability and project filters are
available. Rows use the existing inventory data model (project, block, plot,
category/type/status and booking/member fields when present); no new plot
records are created. The result is capped at 1,000 rows.

2. Plot Merging Register & History

GET /api/v1/reports/sales/merges reads webv9_plot_merges and related project,
plot, member, booking, and user records. It reports source/original and
resulting plots, source/result booking and customer, both project/location
references, merge/effective and workflow timestamps, decision remarks,
submitter/approver, merge event history, and financial transfers from
SalesWorkflowRepository. It requires both source and target projects to be
within the caller's active scope; partial visibility of a cross-scope merge is
not allowed.

Filters: merge date range, status, project, location, customer/member number.
Summary: row count grouped by status for returned rows. Maximum 1,000;
truncation is indicated and totals are explicitly marked as limited to
displayed rows. No live DB execution verified.

3. Plot Cancellation / Refund Register

GET /api/v1/reports/sales/cancellations reads cancellation, booking, plot,
member, project, user, refund-disbursement, workflow-event, and settlement-line
data. Fields include cancellation/booking/plot references, requested date,
raw cancellation status/reason, submitted and decision dates, approver and
decision remarks, approved deductions/refund, project/location/customer,
refund status, refund/posted amount, payout reference, refund approval and
completion dates, event history, and settlement lines.

Filters: cancellation date range, raw cancellation status, raw refund status,
project, location, customer/member number. The report preserves source statuses;
it does not relabel an unrecognized state as approved/completed/rejected.
No live DB execution verified.

4. Overdue Receivables Aging

GET /api/v1/reports/finance/receivables-aging computes outstanding as
max(original_amount + surcharge_amount - adjustment_amount - paid_amount, 0)
from webv9_receivables. Only positive balances with due_date before the
selected as-of date are returned. Aging is explicitly measured as
DATEDIFF(asOfDate, due_date), with buckets 1-30, 31-60, 61-90, and 90+ days.
The source is receivables, not a verified instalment schedule/collection
reconciliation.

Filters: as-of date, due-date from/to, bucket, project, location, customer,
member number or registration number. Summary reports outstanding by bucket,
counts and overall amount for returned rows. A SQL bind-order defect and an
immutable-summary mutation defect found during testing were corrected.

5. Finance Receipt Register

GET /api/v1/reports/finance/receipts reads payments_receipts and payment
allocations. It exposes receipt number/date/amount/method/status, references,
verification/posting dates, customer/member, and authorized allocation
locations. Date, status, payment method, location, and customer filters are
supported. Summary includes count and amount by status for returned rows.
Rows with allocations across any unauthorized project are excluded in full;
partial allocation visibility is not permitted.

C. ACCESS, EXPORT, AND KNOWN CONTROL GAPS

New report APIs under /api/v1/reports/{plots,sales,finance} require Reports/VIEW
plus Plots & Sales/VIEW or Finance/VIEW for the corresponding source. Backend
checks remain authoritative even if a client manually calls an endpoint.
ProjectAccessService supplies active project IDs only for active accounts,
active positions, compatible departments, valid access dates, active projects,
and matching project/location/city scope. The existing permission resolver
also checks designation grants and user overrides. Super Admin uses the
existing system-wide bypass.

The Reports UI is shown only when the current user has Reports access; it only
offers report types whose source-module view is present. Export runs in the
browser over the same authorized/truncated data, not through an unguarded
download route. CSV cells are quoted and formula-leading text is escaped.
Excel output is HTML-table compatible .xls, not an XLSX workbook. Print/PDF
uses the browser print dialog; print styles hide report controls.

The legacy GET /api/v1/reports/summary remains a separate, Super-Admin-only
system-wide count summary. It is not the new scoped Reports workspace and has
no date/project filters. The Dashboard is also system-wide and Super-Admin
gated. User/role and audit APIs remain separate admin surfaces, not new report
exports.

Checked-in SQL files did not contain DDL for the workflow/report tables used by
the new register queries. Runtime schema compatibility must be confirmed
against the actual deployment before release. Existing system screens/APIs
outside the new ReportsController must be independently reviewed before
assuming every financial or customer-care list has identical project scope.
